# TRS系统 功能设计文档编写

> AI辅助编写企业级追溯系统（Traceability & Recall System）功能设计文档的完整方法论。

**当前版本：V4.2（2026-09-24）**

> ## ⚠️ 本仓库是**发布投影，不是权威**
>
> - **唯一权威（SSOT，可写）**：本地分层体系 —— `trs-prd-writer`（编排层）+ `trs-spec-style` / `trs-evidence` / `trs-truth` 等纪律层。
> - **本仓库内容由脚本自动生成，禁止手改** —— 手改即二次分叉。
> - `SKILL.md` 的附录 A / B / C 是纪律层的**内联副本**，仅为离线自包含；与 SSOT 冲突时**一律以 SSOT 为准**。

---

## 这个 Skill 是做什么的？

TRS（供应链追溯系统）功能设计文档，是连接**业务需求**与**技术实现**的桥梁。

它的读者既有不懂技术的业务人员，也有需要精确字段定义的后端开发。传统文档要么"业务看了满意、技术实现时全是坑"，要么"技术细节堆满、业务人员看不懂"——这个 Skill 的目标，就是写出一份**双方都能用**的文档。

---

## 解决什么问题？

| 💢 痛点 | 💡 本Skill的解法 |
|--------|------------|
| 内部稿和客户终稿写成同一份，客户看到一堆内部话术 | 交付模式二分：`INTERNAL` / `CLIENT-FINAL`，两套章节范围 |
| 文档写了"不做什么""假设待确认"，客户读完反而没信心 | `CLIENT-FINAL` 减法清单：Out of Scope / 假设表 / 验收标准一律不写 |
| 字段值列表和校验规则靠拍脑袋，开发实现时全是坑 | 值列表 5 要素 + 校验 3 要素 + 取值一律现查 |
| 追溯系统有特殊性（谱系/召回/审计），新手容易遗漏 | 追溯领域 6 大补充项强制覆盖其一 |
| 接口字段写了但实现时发现各种边界没定义 | 数据项 12 列规范 + 接口契约业务化（双读者可读） |
| 文档面向业务和开发双读者，混在一起谁都看不懂 | 分层章节结构 + 接口契约业务化 |

## 动笔前必须先定两件事

### ① 交付模式（决定章节范围）

| 模式 | 交付对象 | 章节范围 |
|------|---------|---------|
| `INTERNAL` | 团队评审、自检、过程推演 | 完整章节，可含假设表 / 门禁 / 质控报告 |
| `CLIENT-FINAL` | 发给甲方的正式交付物 | **仅六章功能设计本体** |

### ② 工作模式（决定从哪条路走）

| 条件 | 走法 |
|------|------|
| **已有一篇文档要改 / 补 / 拆** | **存量改造**（实际最高频） |
| 手上有可运行的真实代码（前后端仓库） | **代码驱动** ⭐ 有代码时优先 |
| 用户提供了 HTML / 图片 / Figma 原型 | **原型驱动** |
| 用户口头描述需求 | 传统需求沟通（5W1H 挖掘） |

> **代码是事实，原型只是呈现。** 有代码时优先代码驱动：从真实代码反推界面骨架与字段。

## `CLIENT-FINAL` 六章制（发给客户的唯一允许结构）

```
1 文档控制        → 1.1 更改记录（日期/作者/版本/一句话）
2 前言            → 2.1 说明（功能定位一句 + 需求来源一句）
3 问题定义与用户画像 → 3.1 核心问题陈述 / 3.2 用户画像 / 3.3 使用场景分析
4 概述            → 4.1 业务背景 / 4.2 概念说明 / 4.3 核心问题 /
                    4.4 开发目的 / 4.5 使用说明 / 4.6 范围【仅 In Scope】
5 总体设计        → 5.1 功能总体说明 / 5.2 界面流转 / 5.3 用户流程图 /
                    5.4 功能列表汇总 / 5.5 功能依赖说明
6 详细设计        → 每功能：6.x.1 界面设计及交互 / 6.x.2 核心逻辑 / 6.x.3 数据项设计（12 列）
                    公共：值列表说明 / 交互说明 / 补充逻辑 / 接口契约（业务视角）
```

> ⚠️ 六章制、减法清单、以及"不写假设/待确认"这几项，**只在代码驱动这条路上适用**。
> 从原型驱动或需求描述驱动进来时不要照搬。
> 各章填写说明详见 `reference/document-structure.md`。

### 减法清单（`CLIENT-FINAL` 一律删除，无需再问）

| 一律删除 | 归类 |
|---------|------|
| Out of Scope / 范围外 / Non-goals | 边界防御 |
| 假设与待确认表 | 不确定性暴露 |
| 非功能性需求（性能 / 安全 / 审计 / 监控） | 技术设计越界 |
| 发布计划 / 成功度量 / 上线 / 试点 / 回滚 / 培训 | 项目管理 |
| 质控报告 / 干系人 / 决策记录 | 内部治理 |
| 未解决问题 / 已解决问题 | 问题跟踪 |
| 参考文档节（内部路径 / 节点 ID） | 内部痕迹 |
| 验收标准 / Given-When-Then | 质量验证越界 |
| "规划中 / 待实现 / 未实现"等实现差距表述 | 暴露需求与实现的落差 |

> **判断口诀**：写"做什么"，不写"不做什么"；写"确定"，不写"待定"；写"功能"，不写"项目"与"过程"。

## 五条硬规矩

### ① 证据优于断言
每个设计决策必须有来源。没有来源的不能写进文档 —— 这一条的正式表述是 **The Iron Law：未经验证的文档声称完整 = 作弊，不是效率**。

### ② 值列表与校验不允许编造
`CLIENT-FINAL` 下取值 / 状态 / 报错文案一律去代码取真值，不得用泛化经验代替。写完一章，该章出现的所有取值必须核过一遍。

### ③ 数据项必须完整（12 列）

```
字段名 / 字段标识 / 字段类型 / 是否必填 / 是否唯一 / 默认值 /
取值来源 / 展示形式 / 校验规则 / 报错文案 / 备注 / 变更记录
```

> ⚠️ 这是**客户终稿 12 列**。另有一套"开发实现 12 列"（控件类型 / 长度 / 新增 / 编辑 / 值列表…），不要混用。
> 完整定义见 `trs-spec-style/reference/data-item-spec.md`。

### ④ 追溯领域补充项必须覆盖
追溯谱系、召回与演练、质量放行冻结、条码标签、审计留痕、集成与一致性 —— 至少命中一项。
`CLIENT-FINAL` 下若不涉及，**直接不写该章节**，禁止写"本功能不涉及 XX，原因是……"这类不适用声明。

### ⑤ 没实现的就不写
代码里找不到的功能一律不写。这是最高优先的一条硬约束，四类落点（未实现 / 已回退 / 需求有而代码零落点 / 死组件）的判据见附录 C。

## 自检质控门（仅 `INTERNAL`）

内部稿写完后触发 5 维度评分（各 20 分，满分 100）：完整性 / 无歧义 / 可追踪 / 一致性 / 数据项完整性。

| 分数 | 等级 | 处置 |
|------|------|------|
| 90-100 | 🟢 优秀 | 直接提交 |
| 70-89 | 🟡 良好 | 自修"可自完善"项，重评后剩余交 PM |
| 50-69 | 🟠 需改进 | 修明显缺口，剩余交 PM |
| < 50 | 🔴 不合格 | 停止，说明核心缺口后再继续 |

**能自己修的**：字段描述歧义、命名不一致、表格留空按上下文推断。
**必须交 PM 的**：业务决策（优先级 / 审批 / 超时阈值）、外部依赖、特殊权限、无文档支撑的业务规则。

> ⚠️ 质控报告属内部产物，**不进客户终稿**。

## 常见问题

**Q：用户说"这功能很简单，不用问那么细"怎么办？**
A：仍执行最小输入集确认 + 至少一个关键字段写全值列表 5 要素。理由见 `reference/writing-discipline.md` —— "这功能简单，跳过检查"是 The Iron Law 明列的违反借口。

**Q：客户终稿里能写"假设与待确认"吗？**
A：不能。假设表属减法清单禁项，直接删除，不要写"本项待确认"。缺的真值去代码查，查不到就不写。

**Q：接口契约需要写 URL 和 JSON 吗？**
A：不需要。功能设计文档是给业务和开发双方看的，不展示 HTTP 方法、URL 路径、原始 JSON。写的是操作名称、用途、字段含义、业务校验规则。

**Q：为什么删掉了"验收标准"和 Given-When-Then？**
A：客户终稿以「功能描述 + 业务校验规则」承载可验证性；验收条目属内部测试设计，外发等于暴露乙方测试口径。

**Q：追溯系统和非追溯系统用同一个 Skill？**
A：核心方法论相同。区别在于 TRS 有 6 大补充领域（谱系 / 召回 / 放行 / 条码 / 审计 / 集成），要求覆盖其一。

## 已知限制

`SKILL.md` 正文中仍有 6 处指向**未内联**的外部 skill（`dingtalk-doc-calling`、`dingtalk-doc-writeback`、`trs-claim`、`trs-doc-remediation-loop`、`trs-doc-revision`、`trs-project-rules`）。这些是进阶用法（云文档回写、整改闭环、量化口径），**不读不影响主流程**，但离线环境下无法解析，待后续裁决是内联还是改为散文描述。
