# TRS系统 功能设计文档编写

> AI辅助编写企业级追溯系统（Traceability & Recall System）功能设计文档的完整方法论。

---

## 这个 Skill 是做什么的？

TRS（供应链追溯系统）功能设计文档，是连接**业务需求**与**技术实现**的桥梁。

它的读者既有不懂技术的业务人员，也有需要精确字段定义的后端开发。传统文档要么"业务看了满意、技术实现时全是坑"，要么"技术细节堆满、业务人员看不懂"——这个 Skill 的目标，就是写出一份**双方都能用、都爱用**的文档。

---

## 解决什么问题？

| 💢 痛点 | 💡 本Skill的解法 |
|--------|------------|
| 需求讨论时聊得很开心，文档写出来不是那个意思 | 强制5W1H + 逐字段确认，减少歧义 |
| 接口字段写了但实现时发现各种边界没定义 | 数据项12列规范 + 校验3要素 + 报错模板 |
| 追溯系统有特殊性（谱系/召回/审计），新手容易遗漏 | 追溯领域6大补充项强制覆盖 |
| 写完了才发现缺字段、缺验收标准、缺假设表 | PRD自检质控门：每写完一章自动评分，缺口当场补 |
| 文档面向业务和开发双读者，混在一起谁都看不懂 | 接口契约业务化 + 分层章节结构 |

## 核心原理：两个工作模式

### 模式A：传统需求沟通
用户口头描述业务需求，AI通过5W1H框架深度挖掘，逐步完善文档。

适用于：会议纪要整理、用户访谈后写文档、没有原型的从零需求。

### 模式B：原型驱动 ⭐（推荐）
用户提供HTML页面、图片或Figma设计稿，AI先理解原型结构，输出摘要后与用户确认，再生成PRD。

适用于：已有UI设计稿、需要从原型逆向生成文档、减少反复沟通。

> **为什么原型驱动更推荐？** 原型是用户真实意图的载体，比口头描述更准确。AI先读原型 → 输出理解摘要 → 用户确认 → 补充细节 → 写文档，每一步都有用户把关，减少返工。

## 五大核心原则

### ① 证据优于断言
每个设计决策必须有来源：用户确认的 → 标注"用户确认"；按假设写的 → 标注"假设+风险等级"；没有来源的 → 不能写进文档。

### ② 接口契约面向双读者
技术细节（HTTP方法/JSON/URL路径）不写在功能设计文档里，由后端工程师按规范自行补充。文档里写的是：操作名称、用途、字段含义、业务校验规则——业务人员和开发都能看懂。

### ③ 数据项必须完整
每个字段都要定义12个属性：序号、字段名、控件类型、数值类型、长度、必输、新增、编辑、值列表、默认值、校验规则、其他说明。留空必须有理由。

### ④ 追溯领域补充项必须覆盖
TRS系统有特殊性：追溯谱系、召回演练、质量放行、条码标签、审计留痕、集成一致性——至少命中一项并写进文档；如果真的不涉及，必须写明"明确不适用原因"。

### ⑤ 写完必须自检
每完成一个关键章节，AI自动触发质控评估（5维度评分）。能自己修的当场修；修不了的写入"假设与待确认"表，标注优先级，让PM去确认。**写作者自己不知道的不等于产品经理也知道。**

## 核心工作机制：PRD自检质控门

文档写完后不意味着就交稿了——质控门是最后一道关。

### 5个评估维度（各20分，满分100）

| 维度 | 问自己 |
|------|--------|
| 完整性 | 所有必填章节都写了吗？ |
| 无歧义 | 有没有"可能""大概""视情况"这种模糊词？ |
| 可追踪 | 功能、验收标准、详细设计能一一对应吗？ |
| 一致性 | 跨章节的字段名、状态值统一吗？ |
| 数据项完整性 | 数据项表格有留空吗？值列表有来源吗？ |

### 评分等级与处置

| 分数 | 等级 | 处置 |
|------|------|------|
| 90-100 | 🟢 优秀 | 直接提交，可选标注亮点章节 |
| 70-89 | 🟡 良好 | AI自修所有"可自完善"项，重评后剩余→PM确认 |
| 50-69 | 🟠 需改进 | 修明显缺口，剩余全写假设表，告知PM |
| < 50 | 🔴 不合格 | 停止，说明核心缺口，请PM补充信息后再继续 |

### 自完善 vs. 标注PM 的判断规则

**✅ AI自行修复（能修则修）：**
- 字段描述歧义 → 更精确描述替换
- 命名不一致 → 统一命名+全局替换
- 数据项表格留空 → 联系上下文推断，以假设补充
- 缺少验收标准 → 自行推导3条Given/When/Then

**❗ 必须标注PM（不能自填）：**
- 涉及业务决策（优先级/审批/超时阈值）
- 涉及外部依赖（第三方接口/数据来源）
- 涉及特殊权限（未经明确授权的角色操作）
- 业务规则无文档支撑（无法从上下文推断）

## 文档输出规格

### 章节结构（11章 + 质控报告）

| 章节 | 性质 | 说明 |
|------|------|------|
| 1. 文档控制 | 🔵 必填 | 版本、审核状态、变更历史 |
| 2. 目录 | ⚙️ 自动 | 自动生成 |
| 3. 前言 | 🔵 必填 | 参考文档、参与人员 |
| 4. 问题定义与用户画像 | 🔵 必填 | 5W1H、用户画像、成功指标 |
| 5. 概述 | 🔵 必填 | 范围、术语、业务背景 |
| 6. 总体设计 | 🔵 必填 | 功能列表、页面关系图 |
| 7. 详细设计 | 🔵 必填 | 数据项12列表格 + 接口契约 |
| 8. 非功能需求 | 🟢 建议 | 性能、安全、兼容、监控 |
| 9. 发布计划与成功度量 | 🟢 建议 | 上线、回滚、验收 |
| 10. 协作与版本管理 | 🟣 可选 | 利益相关者、决策记录 |
| 11. 未解决问题/已解决问题 | 🟣 可选 | 问题跟踪 |
| 质控报告 | ⚙️ 自动追加 | 每轮自检结果 |

### Word导出规范（微软雅黑）

| 样式 | 字号 |
|------|------|
| H1 一级标题 | 18pt **加粗** |
| H2 二级标题 | 14pt 加粗 |
| H3 三级标题 | 12pt 加粗 |
| 正文内容 | 10pt |
| 表格内容 | 小五（9pt） |
| 页眉/页脚 | 小五（9pt） |

> 表格样式：全包黑色框线 + 表头浅蓝底色（#D9E2F3）
> Typora导出Word：偏好设置 → 导出Word → 勾选"使用pandoc模板" → 指定 `reference.docx` 路径

## 快速开始

### 用户想写一个新功能的设计文档

```
用户：我要做一个追溯任务的详情页

Agent：
1. 你有设计原型吗？（HTML/图片/Figma）
   → 有 → 进入原型驱动流程
   → 没有 → 进入传统需求沟通流程

2. 确认输出格式：Markdown直接写，还是最终要导出Word？
   → Word → 告知模板路径（reference.docx）

3. 开始收集最小输入集（Step 0.5）……
```

### 用户发来了一个原型文件

```
Agent：
1. 读取原型文件
2. 输出理解摘要（页面关系 / 功能清单 / 不确定项❓）
3. 向用户确认4类问题（业务背景 / 功能边界 / 状态逻辑 / 异常处理）
4. 补充业务细节
5. 编写PRD
6. 触发自检质控门
7. 输出质控报告
```

## 常见问题

**Q：用户说"这功能很简单，不用问那么细"怎么办？**
A：仍执行最小输入集确认 + 选一个关键字段写值列表5要素。假设需标风险等级。详见 SKILL.md"反失败纠偏脚本"章节。

**Q：用户要我跳过质量检查怎么办？**
A：必须补齐验收标准（每子功能≥3条）；如果坚持跳过，在文档中注明"质量检查已跳过，由产品经理负责审阅"，并让用户明确说"允许按假设继续"。

**Q：接口契约需要写URL和JSON吗？**
A：不需要。功能设计文档是给业务和开发双方看的，不展示HTTP方法、URL路径、原始JSON响应。技术细节由后端工程师按规范自行补充。

**Q：追溯系统和非追溯系统用同一个Skill？**
A：是的，核心方法论相同。区别在于TRS系统有6大补充领域（谱系/召回/放行/条码/审计/集成），这些章节要求"覆盖其一或明确不适用"，不会遗漏。
