# 原型及补充说明承接

先识别这是目标设计原型还是已运行系统的画面。截图和可点击演示通常只能证明可见呈现，不能单独证明保存、授权、调度或导出已经实现。

## 脚本渲染的 HTML 原型

静态 HTML 只有页面容器、内容由脚本生成时，先定位页面渲染函数、数据常量、事件处理和状态计算，按函数输出还原页面。不要因为静态 DOM 为空就判定没有内容，也不要只看首屏 HTML 而漏掉弹窗、抽屉、详情页签和未挂菜单的页面。

界面提示声称已经发生的结果（例如“通知已发送”）不能单独证明对应能力已实现；把提示、实现和未实现部分分开记录。

## 从画面和交互读取

1. 读取用户指定的页面、图片或HTML，梳理页面之间的关系。图片需实际查看；交互行为只有在已操作或已有说明时才作确定描述。
2. 分开记录查询区、列表、表单、弹窗、详情页签与操作入口。列表展示字段和编辑字段各按所在位置整理。
3. 结合用户补充，核对决定业务结果的信息：谁能看和操作、必填及联动、保存/提交结果、状态变化、失败处理。画面没有体现的部分不自动补成规则。
4. 对缺口先用已有研讨结论和相关资料补足；需要业务拍板时，复用 [主入口的技能连接表](../SKILL.md#2-连接使用者已有技能)中的研讨能力。

不为补充文档自动重做原型。只有用户要求制作或试验原型时才复用使用者环境中已有的原型技能；原型完成也不等于业务规则已获确认。

## 原型之后继续完善

后续说明只更新受影响的操作、字段、状态和流程。用户明确确认的新规则与旧原型不一致时，目标设计采用新规则，并在配套记录标明原型待同步的位置；不伪称已修改原型。最新收到的材料若未经确认，不自动推翻已有确认。

原型、代码和设计并存时，按本次写作目标处理：写新设计采用已确认需求；还原现状则核对代码，不用原型补出代码没有证明的功能。关键冲突留待确认，不静默选一方。

## 核对可达性与一致性

逐个核对菜单、按钮、弹窗是否有对应的渲染和事件处理，记录：只有处理代码没有入口、入口调用不到、界面标签与实际筛选或取值不一致、下拉选项与来源列表不一致。这类情况放入配套记录，不写成业务规则，也不自行补成需求。

无入口的页面不进入正文的页面清单、角色、主流程和详细设计，只在配套记录列出并等待用户确认是否纳入；全局入口不属于本次点名范围时，只写与本次功能的关系，不单独展开。

## 完成条件

本次范围内的页面与动作都有文档归属，画面提供的信息、用户补充的规则和未决事项能分别找回。按 [共用写作规范](writing.md)形成正文；可引用真实原型图片，缺图时用清楚的文字说明，不伪造截图或强制生成HTML。
