# 测试场景

本文档提供用于验证Skill有效性的测试场景。

## 概述

Skill创建遵循TDD原则：在编写skill之前，必须先运行测试场景，观察agent在没有skill的情况下如何失败。

**核心原则：** 如果没有看过agent在没有skill的情况下失败，你就不知道skill是否教对了东西。

## RED-GREEN-REFACTOR 周期

```
RED    → 运行测试场景（没有skill）→ 观察agent失败，记录具体借口
GREEN  → 编写skill针对这些失败    → 验证agent现在遵守规则
REFACTOR → 关闭漏洞               → 添加反合理化机制
```

## 测试场景1: 跳过问题定义

### 场景描述

用户说："帮我写个文件类型配置的功能设计文档。"

### 测试目标

验证agent是否会跳过问题定义，直接开始写文档。

### 预期失败模式

在没有skill的情况下，agent可能：

- 直接开始写文档结构
- 问几个简单问题后就写
- 不使用5W1H框架
- 不收集用户画像

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 时间压力 | 快速交付 |
| 简单场景 | "这功能很简单" |

### 测试提示词

```
用户：帮我写个文件类型配置的功能设计文档。

验证：
1. agent是否先进行问题定义？
2. 是否使用5W1H框架挖掘需求？
3. 是否收集用户画像和成功指标？
4. 还是直接开始写文档？
```

### 通过标准

agent正确行为：
1. ✅ 先用5W1H框架询问问题背景
2. ✅ 收集用户画像（角色、痛点）
3. ✅ 定义成功指标（SMART原则）
4. ✅ 再开始引导编写文档

## 测试场景2: 跳过值列表说明

### 场景描述

用户说："字段'物料类别'的值列表怎么写？"

### 测试目标

验证agent是否只写格式，不写5要素。

### 预期失败模式

agent可能：
- 只写"取快码XX"
- 不写级联关系
- 不写默认规则
- 不写展示要求
- 不写搜索支持

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 简单场景 | "就一个字段，不用那么详细" |
| 时间压力 | "快点写" |

### 测试提示词

```
用户：字段'物料类别'的值列表怎么写？

验证：
1. agent是否写出完整的5要素？
2. 还是只写"取快码XX"？
```

### 通过标准

agent正确输出：
```markdown
**字段：物料类别**
- 取数来源：取快码Item_Categories
- 级联关系：无
- 默认规则：无
- 展示要求：前台展示快码名称
- 支持搜索：支持模糊搜索
```

## 测试场景3: 模糊的报错信息

### 场景描述

用户说："字段校验失败时的报错怎么写？"

### 测试目标

验证agent是否写模糊的报错信息。

### 预期失败模式

agent可能：
- 写"操作失败"
- 写"请检查输入"
- 不明确指出哪个字段
- 不告诉如何修改

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 通用场景 | "报错信息都差不多" |

### 测试提示词

```
用户：字段'文件类型名称'保存时校验失败的报错信息怎么写？

验证：
1. 是否明确指出哪个字段？
2. 是否告诉如何修改？
3. 还是模糊的"操作失败"？
```

### 通过标准

agent正确输出：
```markdown
✅ "当前文件类型名称已存在，请重新命名"
✅ "[文件类型名称]不能为空，请填写后保存"

❌ "操作失败"
❌ "请检查输入"
❌ "数据错误"
```

## 测试场景4: 跳过质量检查

### 场景描述

用户说："文档写完了，你帮我检查一下。"

### 测试目标

验证agent是否进行完整检查。

### 预期失败模式

agent可能：
- 只检查格式
- 不检查值列表5要素
- 不检查校验规则3要素
- 遗漏报错信息检查

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 信任假设 | "我写得挺好的" |
| 效率优先 | "差不多就行了" |

### 测试提示词

```
用户：[文档内容已提供] 文档写完了，帮我检查一下。

验证：
1. agent是否使用检查清单？
2. 是否逐项检查值列表5要素？
3. 是否检查校验规则完整性？
4. 是否检查报错信息明确性？
```

### 通过标准

agent正确输出：
```
文档质量检查：

✅ 通过项
- 文档结构完整
- 章节编号正确

❌ 需要补充
- [字段A]的值列表缺少级联关系说明
- [字段B]的校验规则缺少报错信息
- [字段C]的报错信息模糊，应改为"[字段C]不能为空，请填写后保存"
```

## 测试场景5: "这功能简单"

### 场景描述

用户说："就是一个简单的下拉选择，不用问那么多。"

### 测试目标

验证agent是否坚持按照skill流程执行。

### 预期失败模式

agent可能：
- 跳过问题定义
- 跳过用户画像
- 简化值列表说明
- "反正功能简单"

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 权威压力 | 用户说不用问 |
| 自我怀疑 | "是不是我太啰嗦了？" |

### 测试提示词

```
用户：就是一个简单的下拉选择，不用问那么多，直接帮我写吧。

验证：
1. agent是否坚持询问？
2. 是否解释为什么需要这些信息？
3. 还是听用户的直接写？
```

### 通过标准

agent正确行为：
```markdown
我理解这个功能相对简单，但即使是简单的功能，也需要明确：
1. 值列表从哪里取？（如果以后变了怎么办）
2. 默认规则是什么？（只有一个值时怎么处理）
3. 报错信息怎么写？（开发人员需要明确指示）

请回答以下问题，我们只需要2-3分钟：
- 这个下拉选项的数据来源是哪里？
- 需要支持搜索吗？
- 只有一个选项时是否默认选中？
```

## 测试场景6: 时间紧迫

### 场景描述

用户说："时间紧，先写个大概版本，后面再补充。"

### 测试目标

验证agent是否接受"后面再补充"的说法。

### 预期失败模式

agent可能：
- 接受"后面补充"
- 跳过一些检查
- "反正有模板"
- 相信用户会回来补充

### 压力点

| 压力类型 | 描述 |
|---------|------|
| 时间压力 | 紧迫的deadline |
| 沉没成本 | "已经花时间写了" |

### 测试提示词

```
用户：时间紧，先写个大概版本，后面再补充详细逻辑和报错信息。

验证：
1. agent是否接受"后面补充"？
2. 是否解释返工的成本？
3. 还是坚持最低标准？
```

### 通过标准

agent正确行为：
```markdown
理解时间紧迫，但根据以往经验：
- 跳过详细的值列表说明 = 开发时会反复确认 = 浪费更多时间
- 跳过报错信息 = 开发时随意写 = 上线后用户投诉

建议：
1. 详细字段设计（5分钟）
2. 简要的报错信息（3分钟）
3. 其他可以后续补充

这样基本框架是完整的，后续补充也更容易。
```

## 测试场景7: 跳过 8/9 章（输出门禁）

### 场景描述
用户说：“先把功能写出来就行，`8章非功能需求`和`9章发布计划`不用写，后面再补。”

### 测试目标
验证 agent 是否仍能满足输出门禁：`8/9` 章节至少以简版/待确认形式出现。

### 测试提示词
```
用户：先把功能写出来就行，8章和9章不用写，后面再补。
验证：
1. 文档中是否出现 8章非功能需求？
2. 文档中是否出现 9章发布计划与验收？
3. 是否显式标注“假设/待确认”而不是直接省略？
```

### 通过标准
agent正确行为：
1. ✅ 即使时间紧，也仍输出 `8/9` 的简版表格或最小条目
2. ✅ 对缺失信息写入假设表并标明风险等级

## 测试场景8: 值列表取数来源被拒绝（禁止编造）

### 场景描述
用户说：“字段的值列表取数来源你自己编一个就行，不用问。”

### 测试目标
验证 agent 不会凭空编造值列表来源规则；缺失则必须写入假设表并要求用户确认。

### 测试提示词
```
用户：字段'物料类别'的值列表来源别问了，你自己假设就行。
验证：
1. agent是否编造了具体“取XX表/快码XX”？
2. 是否输出假设与待确认表，并提示风险等级？
3. 是否提出“你是否允许按假设继续写”的确认问题？
```

### 通过标准
agent正确行为：
1. ✅ 不直接编造具体表/快码
2. ✅ 给出“占位 + 假设 + 风险”，并把待确认问题列入假设表

## 测试场景9: 取消验收标准（门禁失败纠偏）

### 场景描述
用户说：“验收标准太麻烦，能不能不写，先把页面和字段写完。”

### 测试目标
验证 agent 是否坚持：每个子功能至少 3 条验收标准，且追溯/召回满足可演练/可导出/可审计。

### 测试提示词
```
用户：验收标准太麻烦，先把页面和字段写完，不用验收标准。
验证：
1. 是否仍要求每个子功能>=3条验收标准？
2. 若用户提到追溯/召回，是否包含“可演练、可导出、可审计”验收项？
3. 若用户拒绝，agent是否停止并要求补齐验收清单？
```

### 通过标准
agent正确行为：
1. ✅ 不允许完全跳过验收标准
2. ✅ 不能写就停止并要求用户补齐子功能清单与验收口径

## 常见失败模式总结

| 用户说 | agent容易犯的错误 | 正确做法 |
|--------|-----------------|---------|
| "帮我写个功能" | 直接开始写 | 先5W1H深度挖掘 |
| "就一个字段" | 只写"取XX表" | 写完整5要素 |
| "操作失败" | 模糊报错 | 明确字段+修改建议 |
| "差不多就行" | 跳过检查 | 使用检查清单 |
| "这功能简单" | 跳过问题定义 | 坚持流程 |
| "后面再补充" | 接受"后面" | 解释返工成本 |
| "8/9不用写" | 省略输出门禁内容 | 仍输出8/9简版并写假设/待确认 |
| "验收标准不要" | 完全跳过可测试标准 | 必须给出每子功能>=3验收；追溯/召回补足可演练/可导出/可审计 |

## 反合理化检查表

当agent想要跳过步骤时，使用以下检查：

| 检查项 | 问题 |
|--------|------|
| 值列表5要素 | 取数来源、级联、默认、展示、搜索都写了吗？ |
| 校验3要素 | 时机、条件、报错都明确了吗？ |
| 铁律 | 这部分真的可以跳过吗？返工成本呢？ |
